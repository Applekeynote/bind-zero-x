# BIND ZERO-X v4.9 — 保守・運用・ソースコード構成設計

## 成熟度と範囲
ローカル研究用アプリケーション。**AWS本番稼働・OpenCV 5・実物GTの確認は未実施**。ここにある運用設計は提案と部分実装であり、AWSデプロイ済みではない。

| 層 | 現行コンポーネント | 責務 | 禁止事項 |

| 受信層 | `api_research.py` | Pydantic検証、認証、HTTP状態、リクエスト上限 | CVアルゴリズムや損失関数の直書き |

**次のリファクタリング指針**：現行 `api_research.py` は依然として太く、依存性注入・`CaptureRepository`/`SessionRepository`のProtocol・設定の中央集約が未完了。実AWS導入前に `/api`, `/application`, `/domain`, `/adapters`, `/tests` のパッケージへ段階的に移管し、既存API契約と回帰テストを保持する。無闇な全面リライトは禁止。

## 2. v4.9で追加した運用上の不変条件

1. `start-captured` はSQLiteでセッションIDを**先に予約**してから原本書込。重複送信はPNG原本の書込前に拒否。
2. `SERVER_CAPTURED_PNG`セッションは、SQLite読込・遷移前に全原本のSHA256を再計算。欠落時は`EVIDENCE_UNAVAILABLE`を返す。
3. `capture_start_reservations` に`PENDING`と`COMMITTED`を記録する。プロセス異常停止した場合、`PENDING`は人間が状態・オブジェクトを監査してから解放する（自動再実行しない）。
4. コンテンツアドレス化したPNGは複数セッションで共用可能であるため、孤立候補は**読取専用で列挙し、自動削除しない**。
5. 物理比較に`E2-ablated`を追加。動画証拠欠落件数を明示し、CSV入力だけでは独立実験を証明しない。

## 3. AWS将来構成（未実装のターゲット）

`Browser (HTTPS/CognitoまたはIdentity Center)` → `CloudFront/WAF` → `API Gateway` → `private VPC / ECS Fargate or EC2 Vision worker (OpenCV 5)` → `S3 versioned originals` + `DynamoDB condition expressions` + `CloudWatch alarms`。人間承認操作は別API、物理介入候補はPCIGゲートと承認確認が両方成立するまで不可。Bedrockは説明生成にのみ任意利用し、ルール計算・証明の権威にはしない。

**分散トランザクション**：DB状態とS3アップロードは原子コミットできない。`PREPARED`→アップロード→SHA照合→`COMMITTED`→`READY`を状態機械として実装し、孤立オブジェクトは保持期間・参照数・法的保持条件を満たした場合に人間承認付きで回収。S3 PUTの成功をSQL COMMITとして扱わない。

## 4. 運用SLO・監視項目（導入前の暫定目標）

| 項目 | 当面の目標 / 監視条件 | 処置 |
|---|---|---|
| API可用性 | 99.5%/月（目標・未測定） | 5xx・503増加でアラート、ロールバック |
| CV処理 | P95 < 5秒（目標・未測定） | 解像度・CPU・トラッカー数を点検 |
| 証拠整合 | 欠落・ハッシュ不一致0件 | 即座に停止/ABSTAIN、原本を再取得 |
| 証明整合 | MAC/証明検算失敗0件 | セッションを隔離、原因調査、秘密鍵ローテーション |
| 物理修正の自動実行 | 常に0件 | 人間承認から独立した危険操作を不可能にする |
| 個人情報 | 元動画をログへ出力しない | 構造化メタ情報のみ保存 |
| 保存容量 | 予算上限の80%で警告 | 参照されないオブジェクトを監査 |

ログ属性：`request_id, session_id_hash, observation_id_hash, trace_id, state_version, capture_receipt_sha256, model_fingerprint, evidence_status, cv_quality, planned_view, disposition, duration_ms`。画像バイト・Bearer token・PIIを出力しない。

## 5. 障害対応ランブック

- **EVIDENCE_UNAVAILABLE**: セッション停止→`python code/operations_audit.py --db ... --archive ... --output audit.json`→原本/マニフェスト確認→取得し直す。ハッシュを上書きして正常化しない。
- **CAPTURE_START_ALREADY_RESERVED**: 二重起動・クラッシュの可能性。DBにセッションがある場合は既存結果を提示し、PENDINGだけの場合は入力とアーカイブの監査後に再受付する。
- **MAC_VALIDATION_FAILED**: 鍵の正当性とDB改変を区別。証拠付きフォレンジック記録とロールバックを優先し、変更済みMACの単純再計算で解決しない。
- **CV品質低下**: 最新カメラ/ROI/校正/照明を点検。推定0mmへのフォールバック禁止。
- **OpenCV 5非対応**: ヘルスは見えるがReady=false。実画像解析しない。CIでランタイムを検証する。

## 6. デプロイ・セキュリティ

- OpenCV5、Python、依存パッケージ、OSベースイメージはDigest/lockfileで固定。SBOM、CVEスキャン、リリース署名を追加。
- コンテナ非root、read-only FS、tmpfsの分離、CPU/メモリ/ファイルサイズ制限、VPC閉域、IAM最小権限、KMSを想定。
- 本番用HMAC秘密鍵はAWS Secrets Manager/KMS、ソルトとは別管理。ローカル鍵ファイルに依存しない。
- データ分類、元画像の保持期間、誤報・再学習フィードバック、個人情報の削除手順を設定。
- 依存ライブラリ更新では再現性/実物GT回帰/互換性テスト後、段階的カナリア配布。前バージョンのスキーマを維持または移行する。

## 7. 保守性・品質ゲート

- 単体/境界値/異常系、API契約、永続化の状態遷移、実物GT、性能、セキュリティ、負荷、停電・再起動復旧、データ保持、障害注入をそれぞれ独立したCI段階にする。
- リリースで試験PASS数だけを根拠にしない。G0「論理健全」、G1「OpenCV 5実働」、G2「AWS」、G3「実物GT」、G4「公平比較」、G5「UX/運用」の各証拠を別の必須署名として要求する。
- 現在の研究用モックで得た結果を、実AWSの実績や実物での効果と記載しない。
